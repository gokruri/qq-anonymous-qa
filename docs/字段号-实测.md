## 一、⚠️ 启动包里的两处错误（已纠正，都是实测打脸）

### 错误 1：`send_packet` 的 `data` 不是业务体，是**完整 OIDB 信封**

启动包把它描述成业务体。实测：`data` = **信封** hex，业务体要自己编码塞进信封的 `f4`。

| 发的 hex | 含义 | 响应 ErrorCode |
|---|---|---|
| `08c41d` | f1=3780（cmd）f2=sub **缺** | 150 `[oidb] no privilege` |
| `08c41d1001` | f1=3780 f2=**1** f4=空 | **0** ✅ |
| `08f6c3c70202` | 把 uin 当 cmd 用 | 145 `[oidb] invalid pkg and decode req failed,...` |

启动包那个「成功样例」`08f2b1a9a302 → ...` 其实只是**查提问总数**（缺了 `1001` 这一半信封）。

### 错误 2：提交回答**不是** `0xec8_1 addComment`

`0xec8` 只是加评论 —— 成功后 JS 做的是 `comment_num += 1`，不是写答案。
真正的回答是 **`0xec7_1 doAnswer`**，命令在 **write 页** bundle（`/v2/anonymous/write`）里：

```js
doAnswer: { str_quest_id: r.qid, str_ans: t.str_ans, uint64_quest_time: r.qtime }
          → "OidbSvc.0xec7_1"
```

> 怎么找到的：answer 页的「编辑答案」跳 `/v2/anonymous/write?...&qid=..&qtime=..`，
> 所以命令不在 answer.js 里，得再扒 write/index.bundle.js 这一层。

## 二、OIDB 信封（实测）

| | 字段 | 类型 | 说明 |
|---|---|---|---|
| **请求** | f1 | uint32 | cmd，如 `3780`(0xec4) / `3303`(0xec7) |
| | f2 | uint32 | sub = `1` |
| | f4 | bytes | **业务请求体** |
| **响应** | f1 | uint32 | cmd 回显 |
| | f2 | uint32 | sub 回显 |
| | f3 | uint32 | **ErrorCode**（0=正常） |
| | f4 | bytes | **业务响应体** |
| | f5 | string | ErrorInfo |

排查判据：
- `145` → `[oidb] invalid pkg and decode req failed,https://iwiki.woa.com/...`
- `150` → `[oidb] no privilege`（sub 写错就是这个）
- **业务体写成非法 protobuf → ErrorCode 变 `100001`**（这是「body 有没有被解析」的判据）

## 三、字段号（实测）

### 3.1 🔑 核心规律：**写页 JS 的键序 == protobuf 字段号序**

bundle 里没有 `.proto`，但每个命令的 JS 对象键是按字段号顺序写的。这条规律经**三次独立验证**：

| 命令 | JS 键序 | 实测出的字段号 |
|---|---|---|
| 0xec4 getAnswerList | uin, quest_num, comment_num, cookie, fetch_type | f1=uin ✅ f2=数量 ✅ f4=cookie ✅ f5=fetch_type ✅ |
| 0xecf getQuestionDetail | uin, comment_num, quest_time, quest_id | f1=uin ✅ f4=quest_id ✅（实测命中） |
| 0xec7 doAnswer | quest_id, str_ans, quest_time | f1/f2/f3（与 0xec8 实测 0 错误码自洽） |

**怎么用**：先从 bundle 抠出 JS 键序，再按序编 f1、f2、f3…，然后用**行为差异**验证（见 3.4）。

### 3.2 0xec4_1 getAnswerList（读）

请求体：

| 字段 | 类型 | 名字 | 实测行为 |
|---|---|---|---|
| f1 | uint64 | `uint64_uin` | 查谁的卡。缺 → 业务 ErrorCode 10002 |
| f2 | uint64 | `uint64_quest_num` | **要几条**。`1..10` 正常，`0` 返空，**`≥11` 服务端直接返空** |
| f3 | uint64 | `uint64_comment_num` | 试了 0/1/10，**无任何影响**（存疑） |
| f4 | bytes | `bytes_cookie` | 翻页游标，回灌上一页响应的 f4 |
| f5 | uint32 | `uint32_fetch_type` | 0/1 正常，≥2 返空 |

响应体：

| 字段 | 类型 | 内容 |
|---|---|---|
| f1 | rpt msg_quest | 提问列表 |
| f3 | uint32 | 提问总数 |
| f4 | bytes | 下一页 cookie：`basetime=..&hasFinish=0/1&pageFeeds=..` |
| f5 | uint32 | **业务 ErrorCode**：0 正常 / 10001 该 uin 不存在 / 10002 参数错 |
| f7 | string | 目标昵称 |

单条 msg_quest：

| 字段 | 类型 | 名字 | 例 |
|---|---|---|---|
| f1 | string | `str_id` | `U_9a4ac46a4692...` |
| f2 | string | `str_quest` | `你是ai吗` |
| f4 | uint64 | `uint64_time` | 提问时间 unix |
| f5 | string | **`str_ans`** | 回答正文（**空串 = 未回答**）|
| f6 | uint64 | | 回答时间 |
| f10 | string | | 评论 id `93_<BOT_UIN>_1791249050_500741` |
| f18 | string | | 32 位 hex 令牌 |

### 3.3 0xec7_1 doAnswer（**写**）与 0xecf_1 getQuestionDetail（读）

```js
0xec7_1  doAnswer          { str_quest_id, str_ans, uint64_quest_time }
0xecf_1  getQuestionDetail { uint64_uin, uint64_comment_num, uint64_quest_time, str_quest_id }
0xeca_1  doEditAnswer      { str_quest_id, str_ans_text, uint64_ask_time, uint64_act_type:5 }
0xec8_1  addComment        { str_quest_id, str_comment, uint64_uin, str_comment_id, uint64_quest_time, uint64_touin }
0xec5_1  getCommentList    { str_quest_id, uint64_comment_num:30, uint64_uin, str_cookie }
0xec9_1  doPraise          { str_quest_id, uint64_uin, uint64_act_type, str_like_key, uint64_quest_time }
0xecb_1  deleteComment     { str_quest_id, str_comment_id, uint64_uin, str_reply_id }
0xeca_1  deleteQuestion    { str_quest_id, uint64_act_type:2, uint64_ask_time, uint64_show_type, uint64_ans_show_type }
0xee5_1  doQuestionExpo    { rpt_quest }
```

`doAnswer` 字段号 = **f1=str_quest_id, f2=str_ans, f3=uint64_quest_time**，实测结果：

```python
body = f_bytes(1, quest_id) + f_bytes(2, "我是🐟，一条住在QQ里的bot，专门陪人唠嗑～") + f_varint(3, 1791501559)
→ 信封 ErrorCode = 0
→ 回读列表：str_ans == 提交的文本  ✅
```

### 3.4 ⚠️ 探测方法论（这条路很难，记下来省下次的时间）

1. **wire type 探测完全无效**：字段号不存在时服务端**静默忽略**，不报错。
   （拿 uin 字段当 bytes 发也返回 ErrorCode 0。）
2. **唯一的解析判据**：业务体写成非法 protobuf → `ErrorCode 100001`。
   这只能证明「body 被解析了」，不能定字段号。
3. **真正管用的办法**：
   - **只读命令优先**：先用 `0xecf_1`（读详情）这种**能安全用真实 id 试**的命令定字段号，
     成功判据是「响应里出现提问正文」。我们就是这样定出 `quest_id@f4`、`uin@f1`。
   - **写命令用伪造 id 探**：0xec7 全程用 `U_deadbeef...T_143_999999999`（不存在的 uin），
     任何请求都写不进真实提问。
   - **看错误码的变化**，不看有没有报错：0xec7 空 body→19，带 f2→16，
     这套消融（f1/f2/f3 各去掉一个）能反推出「哪个字段是必填的」。
4. **JS 键序 = 字段号序**（见 3.1），能直接把候选空间从 8³ 压到 1。

## 四、生产代码 `src/anon-qa.js`

照 `src/qzone-reply.js` 的结构抄（自适应轮询 + 幂等状态 + 最小请求调模型 + dryRun 默认开）。

| 配置（`data/config.json` 的 `anonQa`，全部可省） | 默认 | 说明 |
|---|---|---|
| `enabled` | true | |
| `dryRun` | **true** | 只拉列表打日志，**连模型都不调**（零 token） |
| `intervalMinutes` | 10 | 空闲轮询 |
| `activeIntervalMinutes` | 2 | 发现未答时的密集盯梢 |
| `activeHoldMinutes` | 5 | 盯梢保持时长 |
| `pageSize` | 10 | 每页条数（上限 10） |
| `maxAnswersPerScan` | 3 | 每轮最多答几条 |
| `maxAnswersPerDay` | 0（不限） | |
| `backlogDays` | **3** | **积压闸**：只答最近 N 天的，避免陈年积压一次性炸出几十次模型调用。设 0 = 连积压一起答 |
| `maxAnswerChars` | 150 | 回答长度上限 |
| `silentEnabled` / `silentRanges` | false / `01:00-07:00` | 静默时段 |

幂等与安全（主人定的规矩，代码里逐条落实）：
- `data/anon-qa-state.json` 记 `handled[quest_id]`，**答过的永不重答**
- **提交失败不重试**：网络异常 / ErrorCode≠0 都立刻记 `handled`（宁可漏，别重复烧 token）
- dryRun 下**不调模型**（不是"调了不发"），真正零 token
- 状态文件只留最近 2000 条 id、14 天计数

部署动作（都已执行）：
- 新增 `src/anon-qa.js`
- `src/app.js`：`+ import { startAnonQa } from './anon-qa.js';`，在 `startQzoneReply` 后 `startAnonQa(log)`
